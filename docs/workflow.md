# Workflow — этапы, коммиты, проверки, ревью

Смежные темы: [testing.md](testing.md), [README.md](README.md).

## 1. Git

- `main` — сдаваемая версия. Работа — в ветках `<type>/<slug>`: `feat/send-message`, `chore/setup-tailwind`.
- Merge commit, не squash: история этапов должна читаться проверяющим.
- Коммит и push — только если пользователь разрешил их в этой сессии.

## 2. Иерархия работы

| Уровень    | Что это                       | Правило                                                           |
| ---------- | ----------------------------- | ----------------------------------------------------------------- |
| **Задача** | Одна ветка                    | Одна цель                                                         |
| **Этап**   | Один коммит                   | Законченное изменение, проходит `npm run check` и `npm run build` |
| **Шаг**    | Действие внутри работы агента | Не коммитится                                                     |

- Размер этапа: 5–50 строк — норма, 50–200 — ок, если цельный, > 200 — дробим, < 5 — объединяем с соседним.
- Этап, ломающий сборку или тесты («функцию допишем в следующем») — плохой этап.
- Следующий этап — только после подтверждения текущего пользователем.

## 3. Порядок этапов фичи

1. Если задача вводит правило — **первым коммитом** `docs(rules): …`, до кода.
2. Типы и DTO → чистые функции + тесты → repository → хуки/сервисы → сторы.
3. UI снизу вверх: `shared/ui` → `entities/*/ui` → `features` → `widgets` → `pages` → роутер.
4. Все состояния прогнаны руками: загрузка, пусто, ошибка, данные, мобильная ширина.
5. `npm run check` и `npm run build` зелёные → self-review (§6).

## 4. Коммиты — Conventional Commits

Формат: `<type>(<scope>): <subject>` — **на английском**, present tense, с маленькой буквы.

| Тип            | Когда                          |
| -------------- | ------------------------------ |
| `feat`         | Новое поведение                |
| `fix`          | Исправление                    |
| `refactor`     | Без изменения поведения        |
| `test`         | Только тесты                   |
| `docs`         | `docs/`, README                |
| `style`        | Форматирование                 |
| `perf`         | Оптимизация                    |
| `build` / `ci` | Зависимости, сборка / пайплайн |
| `chore`        | Прочее обслуживание            |

Scope — слайс (`entities/message`, `features/send-message`) или область (`rules`, `infra`).
Тело коммита — место для обратимых технических решений и их причин.

```
feat(entities/message): add notification poller
fix(features/send-message): keep draft when sending fails
docs(rules): add green-api data rules
build(infra): add tailwind and shadcn
```

## 5. Проверки

| Когда                            | Что                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------- |
| Перед каждым коммитом            | `npm run check` (typecheck + lint + format:check + test)                                    |
| Перед push / сдачей              | `npm run build` + ручной сценарий ([testing §5](testing.md#5-ручная-проверка-перед-сдачей)) |
| CI (`.github/workflows/ci.yml`)  | `npm ci` → `check` → `build`                                                                |
| pre-commit (husky + lint-staged) | [инфра]                                                                                     |

Красный `check` — не коммитим. `--no-verify` — запрещён.

## 6. Self-review diff перед коммитом

Формат находки: `путь:строка — проблема (ссылка на правило) — как исправить`.

| Уровень | Что                                                                                                                                                                             | Действие                                        |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| **P0**  | Не выполнен сценарий ТЗ; секрет в логах/URL; утечка (цикл, таймер, подписка без очистки); импорт вверх или кросс-импорт слайсов; `any`/`enum`/`as`/`!`; barrel; `check` красный | Не коммитим                                     |
| **P1**  | Логика в `ui/` или `page`; тернарка/инлайн-стрелка в JSX; цвет/размер мимо темы; файл > 300 строк; дубль логики; неточный текст интерфейса; нет состояния ошибки/пусто          | Исправляем в этом же этапе                      |
| **P2**  | Нейминг, читаемость, мелочи                                                                                                                                                     | Если дёшево; иначе — в список открытых вопросов |

**Не флагаем:** форматирование и порядок импортов (делают инструменты); решения, записанные в `docs/`;
длинные className в сгенерированных shadcn; вкусовщину без правила; отсутствие абстракций «на вырост».

## 7. Зависимости

- Новая зависимость вне стека из [README §1](README.md#1-стек) — только с обоснованием и после согласия пользователя.
- Ставим точной версией: `npm i -E <pkg>` (`-D` для dev). `package.json` руками не правим. Lockfile в git.
- Версии из шаблона Vite с `^` фиксируются точно на этапе инфры [инфра].

## 8. Изменение правил

- Правило меняется отдельным коммитом `docs(rules): …` до кода, который на него опирается.
- Поменял конфиг линтера — обнови раздел «Что запрещено» соответствующего файла в том же коммите.
- Расхождение правил — [README §4](README.md#4-расхождения).

## Что запрещено

- ❌ Коммит без разрешения пользователя, коммит с красным `check`, `--no-verify`.
- ❌ Следующий этап без подтверждения текущего.
- ❌ Смешивать `docs(rules)` и код фичи в одном коммите.
- ❌ Зависимость без согласования, `^`/`~` в новых зависимостях.
