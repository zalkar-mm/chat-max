# Спринт 3 — Получение сообщений

**Цель:** ответ собеседника из MAX сам появляется в нужном чате, без дублей и потерь. После F5 переписка на месте. К концу спринта главный сценарий задания (E-01…E-05) работает целиком на живом инстансе.

**В конце спринта показываем:** вход → новый чат → «Привет» → собеседник отвечает с телефона → ответ появляется в чате. Дальше: пишет новый человек → появляется новый чат. F5 → история на месте. Отключение сети и возврат → сообщения, пришедшие за это время, догружаются.

**Экраны для дизайна:** входящие пузыри (нарисованы в спринте 2), счётчик непрочитанных, кнопка «↓ Новые сообщения», галочки доставки, плейсхолдер неподдерживаемого сообщения, баннеры проблем с получением.

**Зависит от:** спринты 1–2. Перед стартом — результаты спайка: точная форма пустого ответа `receiveNotification`, поля `extendedTextMessage` и `outgoingMessageStatus` (допущения A4–A6, TZ §12.3). Реальные примеры уведомлений сохраняются как фикстуры тестов.

**Подготовка инстанса** (в ЛК GREEN-API, описывается в README): поле Webhook URL пустое; включены входящие сообщения, исходящие сообщения и статусы, статус инстанса (TZ §5.3).

Ссылки `FR-…`, `ST-…`, `OPT-…` — на `docs/TZ.md`, `[DS:…]` — на дизайн-спеку.

## Задача 1 — Фоновое получение сообщений
Связь: E-05, T-07, FR-RCV-01…03, FR-RCV-10, TZ §5.4 · Приоритет: Must · [DS:banner]

### Описание и бизнес-логика
Задание требует получать сообщения через HTTP API GREEN-API. Это не «пуш», а очередь: сервер складывает все события инстанса (входящие, статусы, смена состояния) в очередь и хранит их сутки. Приложение забирает их по одному, по принципу «первым пришло — первым ушло».
Цикл: **забрать** (`receiveNotification`) → **обработать** → **удалить** (`deleteNotification`) → забрать следующее.
Ключевые правила:
- **Удалять нужно всё**, даже то, что нам не нужно (фото, события групп). Иначе очередь «застрянет» на этом событии, и новые сообщения не придут никогда.
- **Удалять только после обработки.** Иначе при сбое сообщение потеряется навсегда.
- **Один цикл на сессию.** Два параллельных цикла забирают события друг у друга и создают дубли.

Запрос забора ждёт до N секунд (long polling): если событий нет, сервер «держит» запрос и отвечает сразу, как только событие появилось. Поэтому ответ приходит почти мгновенно, а сервер не засыпается запросами.

Пользователь этого цикла не видит, он видит только результат: сообщения появляются сами. Видимы только проблемы — баннерами.

### Как должно быть
- Цикл стартует сразу после успешного входа или восстановления сессии и работает, пока пользователь в приложении. В скрытой вкладке **не** останавливается.
- Время ожидания одного запроса — 20 с (допустимо 5–60 по документации).
- Получили событие → обработали (задачи 2–4, 7) → удалили → сразу следующий запрос.
- Пустой ответ (событий нет) → сразу следующий запрос.
- **Сбои:**
  - нет сети / ошибка сервера / «слишком много запросов» → пауза с нарастанием: 1, 2, 4, 8, 16, 30, 30… с; после успешного запроса пауза сбрасывается;
  - браузер вернулся онлайн → новый запрос сразу, без ожидания паузы;
  - удаление не прошло → ещё до 3 попыток, затем продолжаем (дубль отсечёт задача 3);
  - сервер говорит «уже удалено» → продолжаем;
  - событие нельзя разобрать → удалить и продолжать; цикл никогда не останавливается из-за «кривых» данных;
  - креды стали недействительными → остановить цикл, выйти, экран входа с «Сессия недействительна, войдите снова».
- **Остановка** при выходе — мгновенная, текущий запрос отменяется.
- Повторный запуск (переход между экранами, повторная отрисовка) **не** создаёт второй цикл.
- **Баннеры** (компонент из спринта 1):
  - 3+ ошибок сервера подряд → «Сервис GREEN-API недоступен. Повторим через N с» (N — обратный отсчёт);
  - офлайн → «Нет соединения. Переподключаемся…» (из спринта 1).

### Критерии приёмки
1. Собеседник отвечает в MAX → ответ в приложении в течение 2 с при нормальной сети.
2. В сетевой вкладке в любой момент не больше одного активного `receiveNotification`.
3. На каждое полученное событие (в том числе фото, событие группы) уходит ровно один успешный `deleteNotification`.
4. Отключили сеть на минуту, собеседник за это время написал 3 сообщения, включили сеть → все 3 сообщения появились в правильном порядке.
5. Сервер отвечает 500 три раза подряд (мок) → баннер с обратным отсчётом; запросы идут с паузами 1, 2, 4 с…
6. Выход → в сети нет незавершённых запросов к GREEN-API.
7. Событие с битыми данными (мок) удалено, следующее сообщение обработано нормально.
8. Вкладка свёрнута 5 минут, собеседник написал → при возврате сообщение уже в чате.

## Задача 2 — Входящие сообщения в чате и новые собеседники
Связь: E-05, T-03, FR-RCV-04…06, OPT-02, OPT-06 · Приоритет: Must · [DS:bubble-in], [DS:unsupported]

### Описание и бизнес-логика
Входящее сообщение должно попасть в чат того, кто его прислал. Чат определяется по идентификатору отправителя (`chatId`) — тому же, который мы получили при создании чата по номеру. Поэтому в спринте 2 отправляли только по `chatId`.
Если пишет человек, с которым чата ещё нет, создаём чат автоматически. Иначе сообщение будет потеряно: из очереди оно уже удалено.
Имя собеседника: при создании по номеру мы знаем только номер. Во входящем сообщении приходит имя (из контактов или профиля MAX). Если название чата было номером — заменяем на имя, номер остаётся под ним в шапке.
Задание требует только текстовые сообщения. Фото, файлы, стикеры не поддерживаем. Но если собеседник их прислал, честнее показать плейсхолдер, чем молчать.

### Как должно быть
- **Учитываем:**
  - входящие текстовые сообщения;
  - текстовые сообщения со ссылкой (в MAX это отдельный тип — «расширенный текст»; берём только текст).
- **Чат:**
  - есть с таким `chatId` → добавить сообщение;
  - нет → создать чат и добавить сообщение. Название по приоритету: имя из контактов → имя профиля → название чата → идентификатор.
- **Имя:** если название чата — номер, а пришло имя → название меняется на имя; в шапке под именем остаётся номер.
- **Пузырь** слева, время — время отправки собеседником (не время получения).
- Чат поднимается наверх списка, превью — текст сообщения (без «Вы: »).
- **Неподдерживаемые типы** (фото, видео, файл, голосовое, стикер, контакт, геопозиция): пузырь-плейсхолдер курсивом «Сообщение этого типа не поддерживается» (Could; если не успеваем — молча пропускаем, но удаление из очереди обязательно).
- **Групповые чаты** — игнорируем полностью (группы вне scope); событие удаляется.
- Новые сообщения в ленте объявляются скринридером (вежливо, не перебивая).

**Состояния для дизайна:** входящий пузырь, группа входящих подряд, плейсхолдер неподдерживаемого сообщения, новый чат от входящего (в списке), шапка «Имя + номер».

### Критерии приёмки
1. Собеседник ответил в созданный по номеру чат → сообщение слева в этом же чате, не в новом.
2. Пишет человек, которого нет в списке → новый чат наверху, с его именем, сообщение внутри.
3. Чат назывался `+7 999 123-45-67`, пришёл ответ с именем «Анна» → чат называется «Анна», номер в шапке под именем.
4. Сообщение со ссылкой → отображается его текст.
5. Собеседник прислал фото → плейсхолдер (или ничего, если Could не сделан); следующие текстовые приходят нормально.
6. Сообщение в групповом чате → в приложении ничего не появилось, событие удалено из очереди.
7. Время входящего = время отправки в MAX.

## Задача 3 — Без дублей: свои сообщения и сообщения с телефона
Связь: FR-RCV-03, FR-RCV-07, OPT-04, TZ §5.5 · Приоритет: Must (дубли), Could (сообщения с телефона) · [DS:bubble-out]

### Описание и бизнес-логика
Через очередь приходят не только входящие, но и «эхо» наших отправок: сервер сообщает «сообщение, отправленное через API, ушло». У нас оно уже есть в ленте (спринт 2) — показывать второй раз нельзя.
Дубли возможны и при сбоях: если удаление из очереди не прошло, то же событие придёт снова.
Защита одна: у каждого сообщения уникальный идентификатор от API. Если сообщение с таким идентификатором уже есть — второе не добавляется.
Сообщения, которые пользователь написал с телефона в MAX, тоже приходят в очередь. Показать их — значит, переписка в приложении совпадает с перепиской в MAX (Could, зависит от настройки «исходящие сообщения» в ЛК).

### Как должно быть
- Ключ сообщения — идентификатор от API.
- **Эхо своей отправки:** идентификатор уже есть → ничего не добавлять.
- **Эхо пришло раньше, чем ответ на отправку** (редкая гонка) → не дублировать; если за 30 с отправка так и не подтвердилась — показать как своё сообщение.
- **Повторно пришедшее входящее** → не добавлять.
- **Отправлено с телефона / из другой вкладки** (Could) → добавить справа как своё, со статусом «отправлено», в чат по `chatId` получателя (создать чат, если нет).

### Критерии приёмки
1. Отправили «Привет» → в ленте ровно одно «Привет» после прихода эха.
2. Одно и то же входящее событие доставлено дважды (мок) → в ленте одно сообщение.
3. (Could) Пользователь написал собеседнику с телефона → сообщение справа в соответствующем чате.
4. Сообщения из разных источников стоят в ленте по времени.

## Задача 4 — Статусы доставки: «доставлено», «прочитано», «не доставлено»
Связь: OPT-03 (Should), OPT-05 (Could), TZ §5.7 · Приоритет: Should / Could · [DS:message-status]

### Описание и бизнес-логика
Ответ на отправку («принято», спринт 2) не гарантирует, что сообщение дошло. По документации GREEN-API отправка может быть «принята», но не выполнена. Окончательный результат приходит через очередь как событие статуса сообщения.
- **Should:** «не доставлено» — без него интерфейс будет показывать «отправлено» у сообщения, которое не ушло.
- **Could:** «доставлено» и «прочитано» — две галочки как в web.max.ru, почти бесплатно, раз события уже приходят.

Конкретные значения статусов сверяются по реальным событиям из спайка (допущение A6).

### Как должно быть
| Событие статуса | Отображение у своего сообщения |
|---|---|
| Отправлено | одна галочка (уже есть со спринта 2) |
| Доставлено (Could) | две галочки |
| Прочитано (Could) | две галочки акцентного цвета |
| Не доставлено (Should) | красная иконка + «Не доставлено. Повторить» (как ошибка отправки в спринте 2) |

- Статус только повышается (отправлено → доставлено → прочитано). Опоздавшее «доставлено» после «прочитано» ничего не меняет.
- Статус пришёл раньше подтверждения отправки → применяется, когда сообщение получит идентификатор.
- Статус последнего своего сообщения дублируется в превью списка (если заложено в DS).

### Критерии приёмки
1. Событие «не доставлено» (мок) → у сообщения ошибка и «Повторить».
2. (Could) Получатель открыл чат в MAX → у сообщения «прочитано».
3. «доставлено» после «прочитано» → остаётся «прочитано».

## Задача 5 — Непрочитанные и новые сообщения
Связь: FR-LIST-04, FR-RCV-11, FR-VIEW-04 · Приоритет: Must · [DS:unread-badge], [DS:new-messages-button]

### Описание и бизнес-логика
Пользователь должен замечать новые сообщения, даже если смотрит в другой чат, листает историю или ушёл в другую вкладку браузера.
Счётчик локальный: отметки «прочитано» в MAX не отправляем — это отдельный метод API, вне scope.

### Как должно быть
- **Счётчик в списке:**
  - входящее в чат, который не открыт, → +1;
  - открыли чат → счётчик обнуляется;
  - больше 99 → «99+».
- **Открытый чат, вкладка видима** → счётчик не растёт.
- **Вкладка браузера скрыта:**
  - входящее → заголовок вкладки `(3) MAX-чат` (общее число непрочитанных);
  - вернулись во вкладку → входящие в открытом чате считаются прочитанными, заголовок обычный.
- **Пользователь прокрутил ленту вверх** (дальше 100 px от низа) и пришло сообщение:
  - лента не прыгает;
  - появляется кнопка «↓ Новые сообщения» (с числом);
  - нажатие → прокрутка вниз, кнопка скрывается.
- **Пользователь внизу ленты** → новое сообщение плавно прокручивается в вид (без анимации при «уменьшении движения» в настройках системы).

**Состояния для дизайна:** счётчик 1, 12, 99+; кнопка «↓ Новые сообщения» с числом и без.

### Критерии приёмки
1. Открыт чат А, пишут в чат Б → у Б счётчик 1, чат Б поднялся наверх.
2. Открыли Б → счётчик исчез.
3. Вкладка скрыта, пришло 2 сообщения → заголовок вкладки «(2) …»; вернулись → обычный.
4. Прокрутил чат вверх, пришло сообщение → позиция не изменилась, появилась «↓ Новые сообщения».
5. Внизу ленты → новое сообщение видно без действий.

## Задача 6 — История сохраняется после перезагрузки
Связь: OPT-01, FR-AUTH-12, DM-03 · Приоритет: Should · —

### Описание и бизнес-логика
После обработки сообщение удаляется из очереди GREEN-API навсегда. Если не хранить его у себя, F5 оставит пустые чаты. На проверке это почти наверняка случится и будет выглядеть как баг.
Храним в браузере, отдельно для каждого инстанса. Под другим `idInstance` — другая история.
Выход удаляет историю этого инстанса (чужой компьютер, приватность).

### Как должно быть
- **Сохраняются:** список чатов (название, номер, `chatId`, счётчик непрочитанных), сообщения со статусами.
- **Ограничение:** последние 500 сообщений на чат; более старые удаляются при сохранении.
- **Сообщения «отправляется»** на момент перезагрузки → после F5 показываются как «не отправлено» с «Повторить» (неизвестно, ушли ли они).
- **Место:**
  - «Запомнить меня» выключен → история живёт до закрытия вкладки (как и креды);
  - включён → между запусками браузера.
- **Повреждённые данные / нет места в хранилище** → приложение работает с пустой историей, не падает.
- **Выход** удаляет историю текущего инстанса.

### Критерии приёмки
1. 2 чата с перепиской → F5 → чаты, сообщения, статусы, счётчики на месте.
2. Сообщение «отправляется» во время F5 → после перезагрузки «не отправлено» + «Повторить».
3. Выход → вход тем же инстансом → история пустая.
4. Вход другим инстансом → видна только его история.
5. Повреждённые данные в хранилище (вручную) → приложение открывается с пустой историей, без экрана ошибки.

## Задача 7 — Проблемы с получением: понятные сообщения
Связь: ST-14, ST-15, ST-17, ST-18, FR-RCV-08, FR-RCV-09, OPT-07 · Приоритет: Must (ST-14/15/17/18), Could (OPT-07) · [DS:banner]

### Описание и бизнес-логика
Самая частая жалоба «ответ не приходит» — это настройки инстанса, а не приложение. Типичные случаи:
- задан Webhook URL — тогда HTTP API получения не работает;
- инстанс разлогинился (вышли из сессии на телефоне);
- исчерпан лимит бесплатного тарифа.

Приложение должно сказать, что случилось и что сделать, а не молча перестать получать сообщения. Изменения статуса инстанса тоже приходят через очередь, поэтому реагируем на них сразу.

### Как должно быть
| Ситуация | Что делаем | Текст баннера | Кнопки |
|---|---|---|---|
| Задан Webhook URL | Цикл на паузе | «Получение сообщений отключено: в настройках инстанса указан Webhook URL. Очистите его в личном кабинете и подождите около минуты» | «Открыть личный кабинет», «Проверить снова» |
| Инстанс отключился от MAX (событие смены статуса или ошибка) | Цикл на паузе, поле ввода неактивно | «Инстанс отключён от MAX. Отсканируйте QR-код в личном кабинете» | «Открыть личный кабинет», «Проверить снова» |
| Статус → `suspended` | Цикл работает | Жёлтый баннер из спринта 1 | «×» |
| Статус снова `authorized` | Баннеры инстанса скрываются, цикл и отправка возобновляются | — | — |
| Лимит тарифа (событие или ответ 466) | Цикл работает | «Лимит бесплатного тарифа GREEN-API исчерпан. Часть функций недоступна до смены тарифа» | «×» |
| Сервис недоступен | см. задачу 1 | — | — |
| (Could) При входе в настройках выключено получение входящих или задан Webhook URL | Предупреждение сразу после входа, до первого сообщения | «В настройках инстанса выключено получение входящих сообщений — ответы не будут приходить» | «Открыть личный кабинет», «×» |

- «Проверить снова» → проверка статуса инстанса и возобновление цикла; кнопка в состоянии загрузки.

**Состояния для дизайна:** баннер-ошибка с двумя кнопками, баннер-предупреждение с «×», загрузка на «Проверить снова».

### Критерии приёмки
1. В ЛК задан Webhook URL → баннер про Webhook; после очистки и «Проверить снова» сообщения снова приходят.
2. Инстанс разлогинен на телефоне → баннер «Инстанс отключён», поле ввода неактивно; после повторной авторизации и «Проверить снова» всё работает без перезагрузки страницы.
3. Ответ 466 / событие лимита (мок) → баннер про лимит.
4. Статус вернулся в `authorized` (мок события) → баннеры инстанса исчезли сами.
