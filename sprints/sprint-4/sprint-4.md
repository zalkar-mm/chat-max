# Спринт 4 — Надёжность, адаптив, доступность, тесты

**Цель:** новых функций нет. Доводим то, что сделано в спринтах 1–3, до уровня «сразу берём»: работает на телефоне и с клавиатуры, не ломается в нестандартных ситуациях, покрыто тестами, CI зелёный.

**В конце спринта показываем:**
- главный сценарий на реальном телефоне (iOS Safari и Android Chrome);
- прохождение всего сценария только клавиатурой;
- поведение при двух открытых вкладках;
- чат с 1000 сообщений без тормозов;
- отчёты Lighthouse и axe;
- зелёный CI.

**Экраны для дизайна:** доработки mobile (клавиатура, альбомная ориентация, узкие 320 px), фокус-состояния всех интерактивных элементов, экран «Открыто в другой вкладке», переходы и анимации, скелетоны загрузки.

**Зависит от:** спринты 1–3 закрыты. Если что-то из Must спринтов 1–3 не закрыто — сначала оно, потом этот спринт.

Ссылки `FR-…`, `NFR-…`, `ST-…`, `OPT-…`, `Q-…`, `KPI-…` — на `docs/TZ.md`, `[DS:…]` — на дизайн-спеку.

## Задача 1 — Мобильная версия
Связь: NFR-UI-02, NFR-COMP-01 · Приоритет: Must · [DS:mobile]

### Описание и бизнес-логика
Проверяющий откроет демо с телефона. На мобильном у мессенджера свои проблемы: экранная клавиатура перекрывает поле ввода, «прыгает» высота экрана в Safari, вырезы экрана (чёлка, полоска «домой») наезжают на кнопки. Всё это должно быть решено так же, как в нативных мессенджерах.

### Как должно быть
- **Master-detail:** список ↔ чат; «Назад» в чате; системный жест/кнопка «назад» браузера тоже возвращает к списку, а не уводит с сайта.
- **Клавиатура:**
  - при открытии клавиатуры поле ввода остаётся видимым над ней;
  - лента прижата к низу — последнее сообщение видно;
  - шапка чата не уезжает за экран.
- **Высота экрана:** без «прыжков» при появлении и скрытии адресной строки Safari; ничего не обрезается снизу.
- **Вырезы экрана:** поле ввода и шапка не перекрываются чёлкой и полоской «домой».
- **Касания:** все кнопки — область нажатия не меньше 44×44 px; нет срабатываний по двойному тапу; нет зума при фокусе на поле ввода (iOS).
- **Ширины:** 320, 360, 390, 768, 1024, 1440, 1920 — без горизонтального скролла и наложений.
- **Альбомная ориентация** на телефоне: интерфейс работает, поле ввода доступно при открытой клавиатуре.
- **Форма «Новый чат»** на mobile — полноэкранная, клавиатура не перекрывает кнопку «Создать чат».

### Критерии приёмки
1. iPhone (Safari) и Android (Chrome): весь главный сценарий проходится без проблем с клавиатурой и обрезанных элементов.
2. «Назад» браузера из чата → список, повторно → не уходит из приложения без явного действия пользователя (допустимо: выход со страницы после списка).
3. Фокус в поле ввода на iOS не увеличивает масштаб страницы.
4. На 320 px нет горизонтального скролла ни на одном экране.
5. Все интерактивные элементы ≥ 44×44 px на mobile.
6. На iPhone с чёлкой поле ввода не перекрыто полоской «домой».

## Задача 2 — Доступность: клавиатура и скринридер
Связь: NFR-A11Y-01…03, KPI-6 · Приоритет: Must · [DS:focus], [DS:a11y]

### Описание и бизнес-логика
Доступность — быстрый маркер уровня фронтендера, проверяющие её смотрят. Цель — WCAG 2.1 AA: всё доступно с клавиатуры, всё понятно скринридеру, контраст достаточный, анимации отключаются по системной настройке.

### Как должно быть
- **Клавиатура — весь сценарий:** вход → «Новый чат» → номер → чат → сообщение → переключение чатов → выход, без мыши.
- **Порядок Tab** соответствует визуальному: шапка списка → список → шапка чата → лента → поле ввода.
- **Фокус** виден всегда и на любом фоне (единый стиль по DS); при открытии модалки фокус внутрь, при закрытии — обратно.
- **Пропуск навигации:** ссылка «Перейти к сообщениям» — первая по Tab (видна только при фокусе).
- **Скринридер:**
  - у всех кнопок-иконок есть понятные подписи;
  - список чатов — список; у элемента озвучиваются название, последнее сообщение, время, число непрочитанных;
  - лента — область с названием «Сообщения с <название>»; у сообщения озвучиваются отправитель («Вы»/имя), текст, время, статус;
  - новые входящие объявляются вежливо, баннеры-ошибки — сразу;
  - ошибки полей связаны с полями и озвучиваются при появлении.
- **Контраст:** текст ≥ 4.5:1, крупный текст и иконки ≥ 3:1 — проверить все цвета DS, включая текст в пузырях, время, плейсхолдеры, неактивные кнопки (подписи всё равно читаемы).
- **Масштаб:** при увеличении браузера до 200% интерфейс работает, ничего не обрезается.
- **Уменьшение движения:** при включённой системной настройке анимации и плавная прокрутка отключены.
- **Язык страницы** — русский (для правильного произношения скринридером).

### Критерии приёмки
1. Весь главный сценарий проходится только клавиатурой.
2. Фокус виден на каждом интерактивном элементе.
3. axe: 0 нарушений уровня critical и serious на всех экранах (S1, блокирующие статусы, S2, S3, S4, экран сбоя).
4. VoiceOver (macOS или iOS): входящее сообщение в открытом чате объявляется; ошибка поля номера объявляется.
5. Lighthouse Accessibility ≥ 95.
6. Масштаб 200% — без обрезанного контента и горизонтального скролла главного экрана.
7. С включённым «уменьшением движения» анимаций нет.

## Задача 3 — Работа в двух вкладках
Связь: OPT-08, R6 · Приоритет: Should (повышено с Could: проверяющий легко откроет вторую вкладку) · [DS:other-tab]

### Описание и бизнес-логика
Очередь уведомлений одна на инстанс. Две вкладки забирают события по очереди, и каждая видит только половину ответов. Это выглядит как «сообщения теряются».
Решение как в web-версиях мессенджеров: активна одна вкладка. Остальные показывают экран «Приложение открыто в другой вкладке» с кнопкой «Использовать здесь».

### Как должно быть
- Открыли вторую вкладку с той же сессией → вторая становится активной, первая показывает экран «Открыто в другой вкладке» и останавливает получение и отправку.
- «Использовать здесь» в неактивной вкладке → она становится активной, другая уходит на заглушку.
- Закрыли активную вкладку → оставшаяся остаётся на заглушке до нажатия «Использовать здесь» (без автоматического перехвата).
- Выход в любой вкладке → все вкладки на экран входа.
- Обновление истории в активной вкладке не портит сохранённые данные (пишет только активная вкладка).
- Если браузер не поддерживает механизм связи вкладок — ограничение описано в README, приложение работает как раньше.

**Состояния для дизайна:** экран «Приложение открыто в другой вкладке» + кнопка «Использовать здесь»; desktop и mobile.

### Критерии приёмки
1. Две вкладки → получение работает только в одной; ответ собеседника виден в активной.
2. «Использовать здесь» переключает активную вкладку; во второй — заглушка.
3. Выход в одной вкладке → обе на экране входа.
4. В неактивной вкладке нет запросов к GREEN-API.

## Задача 4 — Полировка состояний и взаимодействий
Связь: TZ §3.3 (ST-01…ST-18), NFR-UX-01 · Приоритет: Must · [DS:motion], [DS:skeleton]

### Описание и бизнес-логика
Впечатление «аккуратного продукта» складывается из мелочей: нет мигания, тексты одинаковые по тону, переходы плавные, ни одно состояние не забыто. Задача — пройти всю матрицу состояний из ТЗ и привести к спеке.

### Как должно быть
- **Аудит матрицы:** каждое состояние ST-01…ST-18 воспроизведено (живым инстансом или моком), сверено с DS, скриншот приложен к PR.
- **Без мигания:** индикаторы загрузки появляются только если действие дольше 300 мс; кнопки не меняют ширину при переходе в «загрузку».
- **Анимации** (по DS, короткие ≤ 200 мс): появление нового сообщения, открытие/закрытие формы «Новый чат», появление баннера, переход список ↔ чат на mobile.
- **Тексты:** единый тон, единая терминология («инстанс», «личный кабинет GREEN-API», «MAX»), без технических слов, без точек в заголовках и кнопках, «ё» по DS. Сводный список всех текстов — в отдельном файле `docs/copy.md` (для удобного вычитывания).
- **Время и даты** везде в одном формате и в часовом поясе пользователя.
- **Обрезка:** длинные имена, номера и превью нигде не ломают раскладку.
- **Пустые и крайние случаи:** 0 чатов, 1 чат, 50 чатов; сообщение из одного эмодзи; сообщение из 4000 символов.
- **Favicon и название вкладки** — по DS.

### Критерии приёмки
1. Для каждого из ST-01…ST-18 есть скриншот, совпадающий с DS (PR-чек-лист).
2. Быстрые действия (< 300 мс) не показывают спиннер.
3. Все тексты интерфейса есть в `docs/copy.md` и совпадают с приложением.
4. 50 чатов в списке и сообщение из 4000 символов отображаются без поломки раскладки.

## Задача 5 — Производительность и длинные чаты
Связь: NFR-PERF-01, NFR-PERF-02, KPI-2, KPI-6 · Приоритет: Must · —

### Описание и бизнес-логика
Мессенджер должен оставаться быстрым при длинной переписке и на слабом телефоне. Узкие места чата: перерисовка всей ленты на каждое входящее сообщение и тяжёлая начальная загрузка. Способ решения выбирает разработчик, мы фиксируем результат.

### Как должно быть
- Чат с 1000 сообщений: открытие ≤ 500 мс, прокрутка плавная, ввод текста без задержек.
- Входящее сообщение не перерисовывает весь список чатов и всю ленту — только изменившееся.
- Ввод в поле не вызывает перерисовку ленты.
- Начальный JS ≤ 200 KB gzip.
- Lighthouse (prod, desktop): Performance ≥ 90, Best Practices ≥ 95.
- Нет утечек: 30 минут работы с регулярными входящими → память не растёт неограниченно.

### Критерии приёмки
1. Тестовые данные: 1000 сообщений в чате → открытие ≤ 500 мс (DevTools Performance), прокрутка без заметных рывков.
2. Отчёт сборки: начальный JS ≤ 200 KB gzip.
3. Lighthouse Performance ≥ 90, Best Practices ≥ 95 — отчёт приложен.
4. Профилировщик React: входящее в чат Б не перерисовывает ленту открытого чата А.

## Задача 6 — Безопасность и чистота
Связь: NFR-SEC-01…04, TZ §11 · Приоритет: Must · —

### Описание и бизнес-логика
Креды GREEN-API дают полный доступ к аккаунту MAX пользователя. Проверяющий может проверить, не утекает ли токен. Задача — финальная проверка, что токен нигде не светится, и закрыть типовые веб-уязвимости.

### Как должно быть
- Токен отсутствует в: консоли браузера, текстах ошибок, URL страницы, истории браузера, исходниках репозитория, логах CI.
- В репозитории нет реальных кредов: проверка в CI (поиск похожих на токен строк), `.env.example` только с заглушками.
- Текст сообщений рендерится только как текст (повторная проверка после доработок).
- На продакшене заголовки безопасности: запрет загрузки скриптов со сторонних доменов, запросы только на домены GREEN-API (и прокси, если есть), запрет встраивания сайта во фрейм.
- Внешние ссылки открываются с защитой от доступа к исходной вкладке.
- В продакшен-сборке нет отладочного вывода и карт исходников с секретами.

### Критерии приёмки
1. Поиск значения токена по консоли, сетевым URL страниц (не API), localStorage-ключам названий, исходникам → совпадения только в хранилище кредов и в запросах к API.
2. CI падает, если в коммите есть строка, похожая на реальный токен.
3. Сообщение `<img src=x onerror=alert(1)>` отображается текстом, alert не срабатывает.
4. Заголовки безопасности видны в ответе продакшен-сервера (проверка securityheaders.com или вручную).

## Задача 7 — Тесты и CI
Связь: Q-01…Q-08, KPI-3, KPI-4 · Приоритет: Must · —

### Описание и бизнес-логика
Проверяющий открывает репозиторий: зелёный бейдж CI и осмысленные тесты на ключевую логику — сильный сигнал. Тесты страхуют то, что сломать проще всего: разбор уведомлений, дедупликацию, нормализацию номера, обработку ошибок. Инструменты выбирает разработчик.

### Как должно быть
- **Unit:**
  - нормализация и проверка номера (все примеры из спринта 2);
  - проверка полей входа;
  - перевод ответов API в ошибки и тексты (все строки таблиц ошибок спринтов 1–3);
  - обработка каждого типа уведомления;
  - дедупликация (эхо, повтор, гонка);
  - сортировка чатов; статусы только повышаются.
- **Компонентные:** форма входа (все состояния), форма «Новый чат», поле ввода (Enter, Shift+Enter, лимит, IME).
- **e2e на моке API:**
  - главный сценарий E-01…E-05;
  - неверные креды;
  - `notAuthorized` → «Проверить снова» → `authorized`;
  - офлайн → онлайн с догрузкой сообщений;
  - повторная доставка уведомления → одно сообщение;
  - F5 сохраняет историю;
  - выход очищает всё.
- **Фикстуры** уведомлений — реальные ответы из спайка (без кредов и личных данных).
- **Покрытие** доменной логики и слоя API ≥ 80%.
- **CI на каждый push и PR:** lint → typecheck → unit/компонентные → build → e2e; бейдж в README.
- **Pre-commit:** lint и форматирование изменённых файлов.

### Критерии приёмки
1. CI зелёный на `main`, бейдж в README.
2. Покрытие доменной логики и API ≥ 80% — отчёт в CI.
3. Все 7 e2e-сценариев проходят в CI.
4. Тестов на живой инстанс в CI нет (только локально, по инструкции в README).
